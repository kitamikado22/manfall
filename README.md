## 概要
モバイル向けの3Dカジュアルゲーム。プレイヤーは穴を操作して、街中のオブジェクトを落としていきます。穴を落とせばレベルアップでき、穴を大きくして成長させられます。NPCなどの他のホールに食べられないようにしながら、巨大なボスを倒すゲームです。

## 資料
`Assets/Scripts`フォルダにソースコードが入っています。

### ソース構成概要
```text
Assets/Scripts/
├── Constants/     # ゲーム定数（成長率・最大レベルなど）
├── Interface/     # IHole, IObstacle, IPausable
├── Hole/          # 穴の共通機能（成長・落下・捕食・物理範囲・地形くり抜き）
├── Player/        # プレイヤー専用（移動・カメラ・PlayerHole ファサード）
├── NPC/           # NPC 専用（ランダム移動・NPCHole ファサード）
├── Obstacle/      # 落下物・ボス・SE
├── Game/          # ゲーム進行（Director, 時間, ポーズ, クリア/オーバー, チュートリアル）
├── StartScene/    # タイトル・分割ロード・画面遷移開始
├── UI/            # ボタン・トランジション・演出
└── Other/         # ユーティリティ（DOTween 拡張など）
```


## アピールポイント
- タイトル画面からエンディング画面、設定画面など**ゲームとして一通り完成させることができたこと**
- `IObstacle`や`IPausable`などのインターフェースを使った設計に挑戦したこと
- 穴の処理を実現するために、**地面のメッシュコライダーから動的に穴の形でメッシュをくり抜いて処理していること**
- `HoleActiveArea`によって、穴の周辺かつ同時に物理演算が有効なオブジェクト数を制限し、負荷を抑えていること

### 穴の当たり判定の動的処理について
`HoleCollider`による地面当たり判定メッシュから動的に穴をくり抜く処理です。

動的にメッシュを更新するような処理にした理由としては、**オブジェクトを落としたときの感覚を滑らかにするためです**。固定の穴の形をしたコライダーを使うと、摩擦係数を0にしたとしてもオブジェクトを落としたときの挙動を滑らかにするのが難しかったです。また、穴はプレイヤーだけでなくNPCも操作するため、二つの穴が重なったときに、固定の穴の形のコライダーはお互いの穴を邪魔しあって穴がふさがれてしまいます。
そこで、一枚の地面のメッシュコライダーから動的に穴をくり抜く処理にしました。

#### 処理の流れ
1. 複数の穴を管理 
   各穴は、自分の情報と穴の形の`PolygonCollider2D`を、エディタ側で `holeTransforms`と`hole2DColliders` に登録します。

2. 地面用の2Dポリゴンコライダーに穴を設定
   `pathCount`に登録されている穴の数だけ増やし、`Path 0`を地面の外周、`Path 1`以降を各穴の輪郭として`SetPath`で書き込みます。

3. 穴の移動・成長に合わせて Path を更新
   `FixedUpdate()`で各穴の`Transform.hasChanged`を見て、変更があった穴だけ`MakeHole2D()`を実行します。頂点はローカル形状 × スケール倍率を掛け、ワールド座標（XZ 平面）へ変換してから地面コライダーに反映します。

4. 2D → 3D メッシュへ変換
   `ground2DCollider.CreateMesh(true, true)` で3Dメッシュを生成し、`ground2DCollider.sharedMesh`に代入して、作成したメッシュを反映させています。

5. メッシュの破棄
   更新のたびに前フレームの `Mesh` を `Destroy` し、メモリリークを防いでいます。

```csharp
// 複数穴対応: ホールの数だけ Path を追加
ground2DCollider.pathCount += holeTransforms.Length;

// スケール・位置を反映して地面からくり抜く
ground2DCollider.SetPath(index + 1, pointPositions);

// 2D ポリゴンから 3D MeshCollider 用メッシュを生成
generatedMesh = ground2DCollider.CreateMesh(true, true);
generatedMeshCollider.sharedMesh = generatedMesh;
```

## 現状の課題と解決策
### 設計・アーキテクチャが弱い
殆どのクラスが`MonoBehaviour`を継承したのみで、オブジェクト指向として役割・責務が曖昧になってます。また、エディタのInspectorでの直接参照を用いてクラス間の結合を行っており、全体的に依存度が高くなっています。今回は規模が小さかったので、そこまで問題になりませんでしたが、RPG要素を入れて大規模化しようと思うと設計が破綻する脆弱性があります。

また、**インターフェースを導入している一方で、継承とインターフェースの違いを理解できておらず実装の共有として使っています。**

`IHole`の`OnEaten()`でプレイヤーとNPCそれぞれで実装していますが、プレイヤーとNPCそれぞれである程度共有できる機能なので、ここではインターフェースを使わず、基底クラス`HoleBase`などを用意して継承させるのが設計として綺麗です。
`IObstacle`もボスと通常の落ちるオブジェクトで処理内容が基本的にあまり変わらないため、インターフェースを使うより先に継承を使って設計できないか考えるべきでした。


#### 改善策
- 基本的に継承を用いてオブジェクト指向的に設計するようにするべきです。クラスの流れとは関係なく、コンポーネント的に機能などをクラスに追加するときにインターフェースを用いて依存度を軽減させます。
- 基本的にエディタのInspectorの直接参照を使って、クラスを直接接続するようにするのを控えるようにします。
- `Update()`などで状態を常に監視するのではなく、イベント駆動にして、処理負荷を軽減させつつ依存方向を逆にしてクラス間の疎結合を実現するべきです。



### データ駆動ができていない
レベルアップに必要な経験値は`HoleGrowth`内のコードに直接テーブルが書かれているため、レベルデザインなどを手軽に行うことが難しくなっています。

#### 改善策
- レベル曲線、オブジェクトの経験値などの定数は**ScriptableObject**を使って管理して、Inspectorでまとめて調整できるようにする
